# 架构设计

## 1. 技术选型

| 层 | 选择 | 理由 |
| --- | --- | --- |
| 前端 | React 19 + TypeScript + Vite | 主流、生态成熟；Vite 构建快；产物 ~96 KB gzip |
| 实时通信 | Socket.IO 4 | 自带断线重连、心跳、请求回执（ack）；WebSocket 被拦时自动退回 HTTP 长轮询，适合微信内置浏览器、移动网络等复杂环境 |
| 后端 | Node.js + TypeScript（`node:http` + `sirv` 静态文件） | 与前端共享规则引擎代码；单进程足够家庭规模；不引入框架 |
| 持久化 | 单个 JSON 文件，原子写入 | 最简单可靠；几十个房间完全够用；服务重启/发版后房间和对局都能恢复 |
| 测试 | Vitest（规则、房间、真实 Socket 联机）+ Playwright（双浏览器会话、7 种尺寸） | 覆盖规则正确性、联机协议与真实界面 |
| 部署 | 阿里云 ECS + Nginx（HTTPS/WSS）+ systemd | 用现有服务器，不买新服务；服务端打包成单文件，服务器上不需要 `npm install` |

刻意没有做的：微服务、数据库、Redis、账号系统、微信小程序。

## 2. 总体结构

```
 手机/平板/电脑浏览器                       阿里云 ECS
┌──────────────────────┐   HTTPS / WSS   ┌──────────┐      ┌──────────────────────────────┐
│ React 界面            │ ──────────────▶ │  Nginx   │ ───▶ │ Node 服务 (dist/server.cjs)   │
│  ├ 大厅/房间/游戏外壳  │ ◀────────────── │ 443 端口 │      │  ├ Socket 网关 + 限流         │
│  ├ 各游戏横竖屏界面    │   完整快照推送   └──────────┘      │  ├ RoomManager（通用房间）     │
│  └ connection.ts      │                                   │  ├ 规则引擎（shared 包）       │
│     断线重连/探活      │                                   │  └ JsonStore → data/state.json│
└──────────────────────┘                                   └──────────────────────────────┘
```

## 3. 服务端权威

- **所有对局状态只存在服务端**。客户端只发送“意图”（如“我要在 (7,7) 落子”），服务端用规则引擎校验后执行，再把结果推给所有人。
- **规则引擎是纯函数**（`packages/shared/src/games/*/engine.ts`）：`apply(state, seat, action) → 新 state | 错误`，不依赖 UI、不依赖网络，可单独测试。
- **胜负只由服务端的 `engine.result()` 判断**，客户端只负责显示。
- **回合校验**在引擎里做（`NOT_YOUR_TURN`），房间层再校验“你是不是这局的玩家”。

## 4. 联机协议

见 `packages/shared/src/protocol.ts`。

- 客户端 → 服务端：`room:create / join / leave / ready / start / addBot / kick / sync / peek`、`game:action`、`profile:set`，全部带 ack 回执，返回 `{ ok: true, ... }` 或 `{ ok: false, code, error }`（`error` 是给老人看的中文）。
- 服务端 → 客户端：
  - `session`：访客身份（playerId + 令牌）
  - `room:snapshot`：**完整的、按座位过滤后的房间快照**（任何变化都推一整份）
  - `room:closed`：房间关闭/被请离

### 为什么每次推完整快照

增量同步在断线、乱序、重复时容易出错。家庭游戏状态很小（五子棋几 KB，牌局也不大），每次推完整快照最稳：客户端**整份替换**，不做合并，不会“错乱”。快照带 `roomVersion`（房间级，任何变化 +1），客户端丢弃同一房间的旧版本。

## 5. 访客身份与断线重连

1. 首次连接时服务端生成访客 ID 和 24 字节随机令牌，令牌存在浏览器 `localStorage`，**服务端只保存令牌的 SHA-256 哈希**。
2. 每次（重新）连接，Socket.IO 握手时自动带上令牌 → 服务端找回同一个玩家 → 找回他所在的房间和座位 → 立即推送当前完整快照。
3. 断线只把座位标记为“离线”，**不判负、不删除**。对手看到“XX 暂时掉线了，等 TA 回来…”。
4. 客户端额外的“探活”（`probeConnection`）：页面从后台回到前台（切微信、锁屏解锁）、网络恢复、bfcache 恢复、窗口获得焦点时，发一个 `sync` 请求，3 秒内没回应就立刻重连。这是因为手机锁屏后 TCP 连接常常“看起来还在、其实已断”。
5. 每次重新连接后的第一份快照无条件接受（服务端可能重启过）。
6. 房间清理：所有人都离线超过 6 小时、或 24 小时没有任何动静才关闭（可用环境变量调整）。

## 6. 防止重复操作与状态错乱

每个对局操作都带：

- `actionId`：客户端随机生成。服务端记录最近 64 个已执行的 ID，**同一个 ID 再来一次直接回复 `duplicate`，绝不重复执行**。
- `baseVersion`：客户端做决定时看到的 `game.version`。服务端版本已经变了就拒绝（`STALE`），客户端自动重新同步。

客户端在请求超时/断线时，会等连接恢复后**用同一个 actionId 重试一次**：如果第一次其实已经成功，服务端回复 duplicate；如果没成功，就正常执行。这样“网络卡了点了两次”“重连后补发”都不会落两子/出两次牌。

E2E 测试里专门测了“同一事件循环内连点两次确认落子”只落一子。

## 7. 信息隐藏（为棋牌游戏准备）

引擎的 `view(state, seat)` 决定某个座位能看到什么：服务端给**每个玩家单独生成快照**，别人的手牌只应以张数形式出现。五子棋没有隐藏信息，`view` 直接返回完整状态；斗地主等游戏必须在 `view` 里把他人手牌、底牌（未翻开前）去掉，并写测试断言快照中不含他人手牌。

电脑玩家（`engine.bot.decide(view, seat)`）也**只能拿到自己的视图**，不能偷看。

## 8. 房间系统（所有游戏复用）

`server/src/rooms.ts` 中的 `RoomManager` 不包含任何具体游戏逻辑：

- 房间号：4 位数字，优先分配吉利号码（8888、6666、1688……，其次全由 6/8/9 组成、豹子号/AABB 等），尽量不带 4（`server/src/codes.ts`）。号码空间小，靠限流保护：错误号码每 IP 10 分钟最多 12 次；对局中和满员的房间不能进入；房主可以请人离开。
- 座位数 = 游戏 `maxPlayers`；房主在 0 号座位；房主退出自动移交。
- 开始条件：座位人数 ≥ `minPlayers`、所有真人在线、非房主都已准备（电脑玩家永远就绪）。客户端用同一规则（`startBlocker`）显示提示。
- 电脑玩家：房主可以把空座位交给电脑（游戏需实现 `engine.bot`）；“和电脑下”= 建房 + 补满电脑 + 直接开局。电脑思考有延迟，且每次执行前检查局面版本，避免过时决策。
- 对局中主动退出：调用 `engine.onLeave`（五子棋判负）；引擎没实现则对局中止（斗地主：本局作废、不计分），快照里返回房间记录的中止结果。
- 累计积分：引擎在 `GameResult.scores` 给出每个座位本局得分（斗地主零和；五子棋赢一局 +1），房间按 playerId 累计，显示在等待房间和结果面板。
- 已在一个对局中的玩家想加入别的房间会被拒绝（`IN_OTHER_GAME`），防止误点链接导致判负。

## 9. 安全与限流

| 项 | 规则 |
| --- | --- |
| 错误房间号尝试 | 每 IP 10 分钟最多 12 次（`join` 和 `peek` 共用），超过需等待 |
| 建房 | 每 IP 10 分钟 30 次 |
| 新访客 | 每 IP 10 分钟 60 个 |
| 消息频率 | 每连接 5 秒 40 条 |
| 消息大小 | 单条 ≤ 32 KB |
| 昵称 | 去控制字符，最多 10 字；界面全部经 React 转义 |
| 真实 IP | 部署在 Nginx 后设置 `TRUST_PROXY=1`，从 `X-Forwarded-For` 读取 |

## 10. 横竖屏布局体系

原则：**不缩放整页、不旋转整页、不提示“请旋转手机”**；横屏和竖屏都是完整设计。

- **视口高度**：JS 把 `window.innerHeight` 写入 `--app-h`（兼容不支持 `dvh` 的旧浏览器，正确处理地址栏伸缩），根节点高度 = `--app-h`，`html/body` 禁止滚动。
- **安全区域**：`viewport-fit=cover` + `env(safe-area-inset-*)`。
- **大厅/房间页**：CSS Grid/Flex + 媒体查询（`orientation`、宽度、矮屏 `max-height: 430px` 紧凑模式）。大厅内容区可内部纵向滚动，页面本身不滚动。
- **游戏页**：每个游戏自己决定排布。五子棋：
  - 测量外层容器（不受内部布局影响，避免反馈循环），比较“横排”与“竖排”哪种棋盘更大来选择排布。
  - **同一套 DOM**，只切换 class 和 grid 模板，所以旋转屏幕时组件不会重建，选中的落点、连接、房间都不丢。
  - 竖屏：根据实际测量的顶栏/玩家栏/操作区高度算出棋盘尺寸，上下留白居中；横屏：棋盘占满高度，右侧信息栏宽度随屏幕从 270 增加到 360–430px。
- **触屏防误触**：点一下先选中（半透明棋子 + 十字辅助线），再点同一位置或“确认落子”才落子；鼠标单击直接落子。棋盘点击自动吸附到最近交叉点，按住滑动不算点击。

E2E 测试在 7 种尺寸下断言：页面无滚动、关键按钮完整可见且 ≥ 48px、棋盘完整可见且 ≥ 屏幕短边 80%、棋盘与按钮/信息栏不重叠；并测试旋转后连接 ID 不变、状态不丢。

## 11. 持久化

`server/src/persistence.ts`：任何变化后 1 秒内合并写入 `data/state.json`（先写临时文件再 rename，原子操作）；收到 SIGTERM/SIGINT 时立即写一次。启动时读回，所有人先标记为离线，等他们自动重连。文件损坏时自动备份并从空状态启动，而不是起不来。
